# Проработка реализации osago-aggregator

## Хранилище для `osago-aggregator`

Хранилище для `osago-aggregator` необходимо и будет использоваться для:

   1. Реализаии асинхронного взаимодействия между компонентами
   2. Хранения созданных заявок на ОСАГО и времени их создания
   3. Управления таймингами ожидания ответа на основании времени в 60 секунд от каждой из страховой компаний, в том числе в случаях планового/аварийного перезапуска экземпляров сервиса `osago-aggregator`
   4. Хранения предложений со стороны страховых компаний
   5. Хранения информации о количестве повторных запросов в страховые компании в рамках одной заявки, а так же данных необходимых для реализации паттернов **Retry**, **Timeout**, **Circuit Breaker**.
   6. С помощью Debezium данные о предложениях будут передаваться в топик Kafka сразу по мере их поступления для последующего считывание сервисом `core-app` и передаче пользователю
   7. Хранения дополнительных данных в случае необходимости

## Способ интеграции между сервисами core-app и osago-aggregator

Необходимости в API между `core-app` и `osago-aggregator` нет, т.к. взаимодействие осуществляется в асинхронном режиме с помощью Kafka. Такой подход улучшает возможности масштабирования, а так же отказоустойчивость. В случае реализации API на стороне `osago-aggregator` можно реализовать дополнительный способ интеграции через API и использовать его как резервный, переключая с помощью механизма feature toggle, например, на случай серьёзной аварийной ситуации или длительного обслуживания кластера Kafka. 

Однако, для возможности взаимодействия без брокера сообщений и реализации других сценариев можно реализовать API со следующими методами:

- `POST /osago` — отправка заявки на ОСАГО.
- `GET /osago/{id}/offers` — получение ответов от страховых компаний по запросу с клиетской части.

## Способ интеграции между web-приложением и core-app

`core-app` поддерживает аналогичные `osago-aggregator` API-методы со схожим, но минимально достаточнм контрактом данных:

- `POST /osago` — отправка заявки на ОСАГО.
- `GET /osago/{id}/offers` — получение ответов от СК по запросу с клиетской части. Используется в случае недоступности WebSocket для получения ответа в режиме **HTTP Short-Polling** (запрос каждые 10 секунд с мгновенным ответом)

Кроме API-методов сервис предоставляет возможность взаимодействовать через WebSocket

## Применённые паттерны отказоустойчивости

В реализации будут использованы нижеперечисленные паттерны:

- Rate Limiter
- Circuit Breaker
- Timeout
- Retry

Точки применения отражены на схеме, описание см. в разделе [Схема работы услуги "Заявка на ОСАГО"](#схема-работы-услуги-заявка-на-осаго)

## Развёртывание в нескольких экземплярах

Сервисы `osago-aggregator` и `core-app` могут быть развёрнуты в нескольких экземплярах. Параллеьная обработка топиков осуществляется с помощью механизма Consumer Groups в Kafka, а топики разбиты на партиции, что гарантирует отсутствие конкурентности за обработку одного и того же сообщения разными экземплярами приложения.

## Схема работы услуги "Заявка на ОСАГО"

1. Клиент заполняет форму в web-приложении и отправляет её в `core-app` с помощью HTTP REST API `POST /osago`
2. `core-app` 
   1. Получает входящий запрос на расчёт осаго, сохраняет запись в БД `core-app-db`. В случае успеха возвращает web-приложению ответ с `HTTP/1.1 201 Created`, в теле ответа указывает Id созданной заявки и ссылку для отслеживания онлайн с помощью WebSocket.

      ```text
      HTTP/1.1 201 Created
      Content-Type: application/json
      Location: /api/osago/123e4567-e89b-12d3-a456-426614174000

      {
         "orderId": "123e4567-e89b-12d3-a456-426614174000",
         "websocketUrl": "wss://api.example.com/osago/updates?requestId=23e4567-e89b-12d3-a456-426614174000"
      }
      ```

   2. Debezium с помощью использования паттерна Transactional Outbox по шаблону Transaction Log Tailing считывает изменения и публикует их публикует событие в Kafka (топик `osago.orders`)
   3. Используется механизм отказоустойчивости **Rate Limiter**, сконфигурированный для регулирования потока создаваемых заявок с учётом имеющихся ресурсов. Он так же действует и для оформляемых заявок через системы партнёров.
3. `osago-aggregator` подписан на топик `osago.orders`, считывает из него информацию по заявкам, сохраняет в БД `osago-aggregator-db` и отправляет запрос в страховую компанию:
   1. Для работы с API страховых компаний используются механизмы отказоустойчивости, обеспечивающие стабильность в процесса:
      - **Timeout** - завершает ожидание ответа от страховой компании, если он не получен за отведённое время
      - **Retry** - повторяет запросы неудавшиеся по техническим причинам. Кроме того, запрос к страховым компаниям будет повторён, если приложение было перезапущено аварийно. Учитывается ограничение в "общие 60 секунд" на подготовку ответа по заявке
      - **Circuit Breaker** - ограничивает запросы к страховым компаниям в случае превышения лимита неудачных вызовов по техническим причинам
   2. При срабатывании Timeout в базе создаётся ответ по заявке, но со статусом "offer-timeout". При таком статусе предложения пользователь будет проинформирован, что нет необходимости в ожидании и сможет принять решение о повторном запросе.
   3. Любой результат обработки сохраняется в базу, откуда с помощью Debezium, на основании изменений в БД, публикуются события в Kafka (топик `osago.offers`)
4. `core-app` подписан на топик `osago.offers`, откуда считывает информацию о предложениях (все сформированных и завершившихся ошибками), интерпретирует результат и обновляет данные в БД `core-app-db` по статусу обработки заявки и отправляет информацию в WebSocket, если он открыт.
5. Если WebSocket открыт, web-приложение получает данные о поступивших предложениях по нему. Если нет, то с периодичностью раз в 10 секунд вызывается метод `GET /osago/{id}/offers` в `core-app` для получения информации о предложениях по заявке
