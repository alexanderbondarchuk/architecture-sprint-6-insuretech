# Анализ и предложение решения архитектурных проблем InsureTech

## Анализ текущей архитектуры в рамках поставленных целей бизнеса

1. При плане развития сервиса во всех регионах РФ и, как следствие, роста количества пользователей - ресурсов одного ЦОД может оказаться недостаточно, а вертикальный рост может быть невозможен или экономически нецелесообразен в связи с неоптимальной утилизацией оплачиваемых ресурсов в часы низкой нагрузки.
2. Бесперебойное обслуживание 24/7 клиентов из всех часовых поясов и доступность (99.9%) так же невозможно при единственном экземпляре сервиса, у которого возможны плановые периоды обслуживания или непредвиденные сбои. В случае аварии - услуги компании становятся недоступными во всех регионах РФ.
3. Невозможно соблюдение требований отказоустойчивости RTO = 45 мин (Recovery Time Objective/Максимально допустимое время простоя системы после аварии до момента её полного восстановления) и RPO = 15 мин (Recovery Point Objective/Максимальный допустимый объём данных, который можно потерять при аварии, измеряется во времени) в связи с отсутствием системы мониторинга и системы алёртинга позволяющих оперативно реагировать на аварии и, как следствие откатываться на бэкап 15 минутной давности. Информация о наличии процесса бэкапирования в действующей системе отсутствует.
4. Отсутствует реализация Rate Limiting для ограничения количества запросов пользователей и API.
5. Отсутствует настройка ограничений под пиковые нагрузки, возможные при проведении рекламных компаний.

## Решение

[Схема решения](InsureTech_технологическая_архитектура-to-be.drawio.xml)

1. Развернуть 2 независимых кластера K8s, failover-стратегия Active-Active. Выбранная стратегия обоснована высокими требованиями доступности и отказоустойчивости. Вариант растягивать зону на два распределённых узла выглядит неподходящим в связи с издержками на поддержание стабильного сетевого соединения между узлами и сложностей сопровождения. Локацию для каждого кластера K8s выбрать с учётом фактора плотности населения РФ и мощности сетевых коммуникаций. Например: 1 ЦОД в Москве для обслуживания от Калининграда до Екатеринбурга, 2 ЦОД в Новосибирке для обслуживания от Екатеринбурга до восточных окраин Камчатки.
2. Развернуть GSLB (глобальный банансировщик) для распределения трафика пользователей по принципу "ближайшего" ЦОД (geoDNS) и/или по принципу "наименее загруженного, а так же при сбоях.
3. Для ускорения загрузки статичных файлов и более равномерной скорости загразки страниц из отдалённых регионов рекомендуется развернуть CDN.
4. Развернуть сервисы сбора логов, метрик и алёртинга (Prometheus, Alertmanager, Grafana, OpenSearch), что позволит вероятность соблюдения требуемого RTO.
5. Развернуть HPA (Horizontal Pod Autoscaler) для автоматизации масштабирования экземпляров сервисов в зависимости от нагрузки. Настроить Cluster Autoscaler для автоматического мастабирования узлов кластера в целях равномерного использования ресурсов.
6. Настроить API Gateway и Rate Limiting для B2B-пользователей API в целях ограничения RPS на одного API-пользователя.
7. Для хранения данных использовать Patroni с PostgreSQL с кластером etcd из 3х нод, для переключения master узла postgres между кластерами. На каждом из K8s кластеров по 1 экземпляру, а так же 1 экзепляр в отдельном ЦОД (третий ЦОД) для обеспечения кворума и отказоустойчивости. Это решение выглядит как минимально жизнеспособное, отвечающее требованиям отказоустойчивости и доступности. Однако, это решение необходимо развивать на дальнейших этапах, т.к. обращение к базе данных на удалённом кластере повышает время обработки запроса, повышает нагрузку на один кластер, что сильно нивелирует преимущества размещение кластеров K8s по критериям, описанным в пункте 1. В качестве дальнейших шагов развития рассмотреть примерение шардирования данных по региональному принципу и использование паттерна Transactional outbox по шаблону Transaction log tailing с помощью Kafka и использования CDC-инструмента (Change Data Capture) Debezium.
