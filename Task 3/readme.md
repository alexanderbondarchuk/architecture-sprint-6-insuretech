# Анализ приложения InsureTech

## Проблемы текущей архитектуры

1. Высокая связность и синхронные вызовы между `core-app`, `ins-comp-settlement` и `ins-product-aggregator`. Взаимодействие по REST снижает отказоустойчивость, при недоступности какого-либо из сервисов заврос, в том числе от внешнего пользователя, падает с ошибкой. Сбой любого из API может замедлить или прервать весь процесс.
2. Отсуствуют механизмы гарантированной доставки данных между сервисами — ошибки приводят к потере данных или задержкам.
3. Линейная зависимость времени работы и агрегации данных `ins-product-aggregator` от количества интеграций с внешними провайдерами страховых продуктов. Вероятность падения процесса целиком повышается из-за планов по росту количества интеграций и возможных ошибок, например, связанных с временной недоступностью любого из внешних провайдеров.
4. Дублирование запросов к `ins-product-aggregator` со стороны сервисов `core-app` и `ins-comp-settlement`, в рамках которых запрашиваются не изменения, а полная информация по всем продуктам. С ростом числа страховых компаний объём данных вырастет, увеличится время отклика и нагрузка на сеть.
5. Несоответствие периодичности запросов между `core-app` и `ins-comp-settlement`, может вызвать рассинхронизацию данных. В целом не понятна бизнес-цель такой интеграции и какие данные в её рамках получает сервис `ins-comp-settlement`, которые не может взять у `core-app`.

## Предлагаемое решение

[Переход на EDA](InsureTech_C4_сontainer-diagram.drawio.xml)

Переход на Event-Driven архитектуру позволит:

1. Перейти с синхронного взаимодействия между сервисами на асинхронное, что снизит связанность.
2. Снизит нагрузку за счёт порционной поставки данных, по мере их поступления.
3. Повысить частоту обмена данными между компонентами системы для своевременного обновления информации.
4. Независимо масштабировать каждый из сервисов, при изменениях нагрузки на систему.

## Описание основных изменений

1. Сервис `ins-product-aggregator` доработать, чтобы интервал запросов к внешним провайдерам страховых услуг можно было конфигурировать через env-переменные и feature toggle. При получении информации изменения будут передаваться в базу данных, откуда с помощью Debezium передаваться в брокер сообщений. Передаваться будет только дельта, что снизит объём сетевого трафика.
2. Сервисы `core-app` и `ins-comp-settlement`, как подписчики на сообщения от `ins-product-aggregator`, в режиме реального времени будут получать сообщения об изменениях по продуктам провайдеров страховых услуг.
3. Сервис `ins-comp-settlement`, как подписчик на сообщения от `core-app`, будет получать информацию о новых заказах на страховку в режиме реального времени, проводить расчёт и передавать эту информацию провайдерам страховых услуг.
